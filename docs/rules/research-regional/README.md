# 地区规则与原开房动态逻辑补查

日期：2026-09-08。研究结论：D03 牌堆、D04 判胡与组合、D05 红黑点仍未定稿。本次新增的是原客户端动态行为证据，未取得原服务端规则实现，未修改玩法引擎或开房配置。

## 火十四“八个十”的新证据

原 `FrameGameConfig` 编号 3 的两项提示分别为：

- 一副牌：`6个10，6个7（4个7加大小王），6个4`。
- 两副牌：`8个10，12个7（8个7加4个大小王），8个4`。
- 八个 10 天胡：`庄家起手8个10天胡算100分`。

仅看静态配置会出现一副牌只有六个 10、却默认勾选八个 10 天胡的表面冲突。原 `CreateRoomUIController.loadGameConfig` 与 `onClickToggle` 另有相同逻辑：在编号 3 且 `_tspx` 引用存在时，以 `!yifupai` 控制该选项显示，并将 `bage10tianhu` 强制写成同一值。这证明原客户端存在“八个十与两副牌联动”的实现意图。

但完整调用路径还有两处覆盖：`onClickGameBtn` 加载配置后，将所有名称不是“勾鱼两副牌”的玩法重新写成 `yifupai=true`；`onLoad` 调用 `loadGames` 创建选项后，又把 `_tspx` 清空。为确认影响，本次执行了原模块工厂和原控制器方法，用最小 Cocos 节点、存储及请求捕获替身做了 7 条隔离复现，9 项结果断言通过。

| 路径 | 提交 `yifupai` | 提交 `bage10tianhu` | 八个十选项 | 说明 |
| --- | --- | --- | --- | --- |
| 直接选择火十四，默认一副牌 | true | false | 隐藏 | 动态逻辑覆盖静态默认值 |
| 直接选择后切两副牌 | false | true | 显示且勾选 | 正常联动路径 |
| 两副牌下取消八个十勾选 | false | true | 显示但未勾选 | 提交值被末尾联动重新开启 |
| 再切回一副牌 | true | false | 隐藏 | 正常联动路径 |
| 保存两副牌后重新选择火十四 | true | true | 显示且勾选 | 牌副数字段被游戏名判断覆盖 |
| 完整原 `onLoad`，默认一副牌 | true | false | 隐藏 | `_tspx` 已清空 |
| 完整原 `onLoad` 后切两副牌 | false | false | 仍隐藏 | 引用清空导致联动未执行 |

原包位置：`assets/assets/hall/index.js` 第 733—734 行的初始化顺序，第 892—893 行的加载与覆盖，第 914 行的选项引用，第 946—949、1049—1052 行的联动。提取文件为 `outputs/apk-deep-analysis/modules/hall/CreateRoomUIController.js`；准确文件哈希见来源索引。

复现只证明原 JavaScript 函数如何生成待提交的开房参数。它没有运行原生 Cocos 渲染、事件系统或服务端；因此不能据此宣布原线上房间一定出现同样问题，也不能推断原服务器是否纠正参数。它没有确定完整实体牌总数、白皮替十是否满足天胡、或八个十的胡牌优先级。

可复现脚本：[reproduce-fire-ui.mjs](reproduce-fire-ui.mjs)，结果：[fire-ui-reproduction.json](fire-ui-reproduction.json)。在共享工作区根目录执行：

```powershell
node outputs/doushisi/docs/rules/research-regional/reproduce-fire-ui.mjs
```

## 对实现的影响

1. 火十四的静态“六个十与八个十”问题已找到动态解释及生命周期反例；应在规则书中保留这两部分证据，而非仅写“已解决”。

3. D03、D04、D05和雷波抢巴继续研究。公开文章、UI默认值和按钮文案都不能替代原服务器裁决，也不构成用户批准。
